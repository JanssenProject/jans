# Cedarling JavaScript maintainer guide

This document explains how `cedarling_js` is built and maintained. The
[package README](../README.md) is the authoritative consumer documentation.

## Repository location and build order

After cloning the Jans repository, the package is located at:

```text
jans-cedarling/bindings/cedarling_js
```

`cedarling_js` wraps the JavaScript glue generated by `cedarling_wasm`.
Install Node.js 20.19 or later, Rust stable, the
`wasm32-unknown-unknown` Rust target, and `wasm-pack` 0.14.0. Always build the
sibling WASM package first, from its own directory:

```sh
rustup target add wasm32-unknown-unknown

cd jans-cedarling/bindings/cedarling_wasm
wasm-pack build --release --locked --target web --scope janssenproject

cd ../cedarling_js
npm ci
npm run build
```

Running `wasm-pack` inside `cedarling_wasm` is significant: its local Cargo
configuration controls the release profile used for the published binary.
The JavaScript package consumes `../cedarling_wasm/pkg` through the local
dependency declared in `package.json`. Run the focused tests and cumulative
gate described in [Tests and local gate](#tests-and-local-gate) after the
initial build succeeds.

## Project structure

```text
cedarling_js/
├── src/                 SDK source
│   ├── entries/         Runtime-specific initialization selected by package exports
│   ├── configuration/   Public configuration validation and normalization
│   ├── client/          Public client behavior and lifecycle
│   ├── engine/          Boundary and adapters for the generated WASM API
│   ├── authorization/   Authorization request and response mapping
│   ├── context/         Context data operations and types
│   ├── issuers/         Trusted-issuer operations
│   ├── logs/            Decision-log operations and mapping
│   ├── values/          Shared value conversion
│   └── errors/          Stable errors and sensitive-detail redaction
├── tests/
│   ├── unit/            SDK behavior with controlled engine doubles
│   ├── contract/        Built SDK against the real sibling WASM
│   ├── e2e/             Packed consumers, module formats, bundlers, and browsers
│   ├── runners/         Host-specific launchers for shared suites
│   ├── fixtures/        Shared policy and runtime test inputs
│   └── types/           Positive and negative public TypeScript contracts
└── scripts/             Build, packaging, staging, and test orchestration
```

Runtime selection is internal. Consumers use the same `createCedarling` API in
every supported runtime and should follow the [package README](../README.md).

## Consumer service map

`createCedarling(options)` returns one `CedarlingClient`. Every service shares
that client's engine instance, configuration, and lifecycle.

| Consumer surface | Features exposed | SDK responsibility before and after WASM |
| --- | --- | --- |
| `client.authorizeUnsigned()` | Authorize application-supplied Cedar entities, action, resource, and context | Validate and detach the request, invoke unsigned authorization, and normalize the decision or error |
| `client.authorizeMultiIssuer()` | Validate mapped JWTs from configured issuers and authorize the resulting entities | Validate token mappings and request shape, invoke multi-issuer authorization, and normalize the result |
| `client.authorize()` | Common entry point for either authorization model | Select the named operation from the explicit request discriminator; it does not choose a trust model heuristically |
| `client.context` | `set`, `get`, `getEntry`, `delete`, `clear`, `entries`, and `stats` | Validate keys, values, and TTLs; detach inputs and outputs; delegate storage and authorization-time context injection to Cedarling |
| `client.issuers` | `isLoaded` by configured issuer ID or exact `iss` value | Require exactly one issuer reference, then normalize the readiness observation |
| `client.logs` | `ids`, filtered `find`, and destructive `drain` | Validate supported query combinations, enforce memory-logging availability, and return detached, normalized log entries |
| `client.close()` | Shut down the client and release WASM resources | Reject new work once closing starts, wait for accepted operations, perform shutdown once, and share the result across repeated calls |

The SDK makes these decisions independently of the Cedarling engine:

- package export conditions select the runtime adapter; there is no runtime
  detection in the public API;
- public configuration and operation inputs are validated, copied, and
  detached before crossing the WASM boundary;
- `authorize()` dispatches only from the caller's explicit `type`;
- expected failures use the stable `Result` and SDK error model, with
  validation paths and redacted details;
- generated decisions, context values, issuer observations, and logs are
  converted into stable JavaScript-owned values;
- operations share one lifecycle guard, and `close()` coordinates concurrent
  work and disposal.

The SDK does not independently decide whether access is allowed, whether a
token or issuer is trusted, or how a Cedar policy evaluates. Those decisions
remain in Cedarling WASM; the SDK validates the JavaScript contract, delegates
the operation, and stabilizes the result.

## Configuration mapping boundary

The public `CedarlingOptions` type in `src/configuration/types.ts` is the
consumer contract. `src/configuration/prepare.ts` is the source of truth for
validating those options, applying JavaScript defaults, and producing the
`CEDARLING_*` bootstrap map passed to WASM. The package README documents only
the JavaScript-facing behavior; the internal mapping is maintained here.

### Policy, logging, and authorization mapping

| JavaScript option | Cedarling bootstrap behavior | Default or notes |
| --- | --- | --- |
| `applicationName` | `CEDARLING_APPLICATION_NAME` | Required |
| `policyStore: { type: "inline", document }` | `CEDARLING_POLICY_STORE_LOCAL` | Serializes the policy-store document |
| `policyStore: { type: "url", url }` | `CEDARLING_POLICY_STORE_URI` | Requires an absolute credential-free HTTP(S) URL |
| `policyStore.refresh.intervalSeconds` | `CEDARLING_POLICY_STORE_REFRESH_INTERVAL` | URL sources only; `0` (disabled); a non-zero value must be at least 5 seconds |
| `policyStore: { type: "archive", bytes }` | Uses the WASM archive-bytes initializer | Does not create a raw bootstrap policy-source property |
| `policyStore: { type: "loader", load }` | Calls the loader once, then uses the WASM archive-bytes initializer | Does not create a raw bootstrap policy-source property |
| `logging` omitted or `{ type: "off" }` | `CEDARLING_LOG_TYPE=off`, `CEDARLING_LOG_LEVEL=WARN` | Logging is optional and off by default |
| `logging.type: "memory"` | `CEDARLING_LOG_TYPE=memory` | Enables `client.logs`; defaults: 60-second TTL, 10,000 items, 500,000 bytes per item |
| `logging.type: "console"` | `CEDARLING_LOG_TYPE=std_out` | Writes through the generated console logger |
| `logging.level` | `CEDARLING_LOG_LEVEL` | Memory/console logging only; `"warn"` |
| `logging.ttlSeconds` | `CEDARLING_LOG_TTL` | Memory logging only; `60` |
| `logging.maxItems` | `CEDARLING_LOG_MAX_ITEMS` | Memory logging only; `10_000`; `0` removes the count limit |
| `logging.maxItemSizeBytes` | `CEDARLING_LOG_MAX_ITEM_SIZE` | Memory logging only; `500_000`; `0` removes the size limit |
| `authorization.dangerouslyDisableSchemaValidation` | Inverts to `CEDARLING_STRICT_SCHEMA_VALIDATION` | `false` means validation is enabled |
| `authorization.decisionLogTokenIdClaim` | `CEDARLING_DECISION_LOG_DEFAULT_JWT_ID` | `"jti"` |

`logging.type` is not an additional Cedarling setting. It is the typed
JavaScript representation of `CEDARLING_LOG_TYPE`. The public values are
`"off"`, `"memory"`, and `"console"` (`"console"` maps to `std_out`). Lock
service delivery is configured separately through `lock`. See the
[Cedarling audit-log reference](https://docs.jans.io/nightly/cedarling/reference/cedarling-logs/#cedarling-audit-logs)
for the underlying concepts.

### HTTP and Lock mapping

| JavaScript option | Cedarling bootstrap behavior | Default |
| --- | --- | --- |
| `http.maxRetries` | `CEDARLING_HTTP_REQUEST_MAX_RETRIES` | `3` |
| `http.retryDelaySeconds` | `CEDARLING_HTTP_REQUEST_RETRY_DELAY` | `3` |
| `http.maxResponseSizeBytes` | `CEDARLING_HTTP_MAX_RESPONSE_SIZE_BYTES` | `10_485_760` |
| `lock` omitted | `CEDARLING_LOCK=disabled` | Lock integration is disabled |
| `lock.configurationUrl` | Enables `CEDARLING_LOCK` and maps to `CEDARLING_LOCK_SERVER_CONFIGURATION_URI` | Required when `lock` is present |
| `lock.ssaJwt` | `CEDARLING_LOCK_SSA_JWT` | Omitted |
| `lock.logIntervalSeconds` | `CEDARLING_LOCK_LOG_INTERVAL` | `0` |
| `lock.healthIntervalSeconds` | `CEDARLING_LOCK_HEALTH_INTERVAL` | `0` |
| `lock.telemetryIntervalSeconds` | `CEDARLING_LOCK_TELEMETRY_INTERVAL` | `0` |
| `lock.logChannelCapacity` | `CEDARLING_LOCK_LOG_CHANNEL_CAPACITY` | `100` |
| `lock.logMaxRetries` | `CEDARLING_LOCK_LOG_MAX_RETRIES` | `5` |

Unknown option fields, including raw `CEDARLING_*` keys, are rejected. See the
[complete Cedarling bootstrap-property reference](https://docs.jans.io/nightly/cedarling/reference/cedarling-properties/)
when comparing the Rust configuration surface with this binding.

Do not add a raw bootstrap-property passthrough. Rejecting unknown fields keeps
misspellings deterministic, prevents generated implementation details from
becoming public API, and lets the SDK use Web-native representations where a
raw property is unsuitable. In particular:

- `inline` and `url` policy sources map to bootstrap properties, while
  `archive` and `loader` use `init_from_archive_bytes`;
- `logging.type` maps `"off"`, `"memory"`, and `"console"` to the current WASM
  values `off`, `memory`, and `std_out`; Lock delivery is configured
  independently through the typed `lock` options;
- `jwt.dangerouslyDisableSignatureValidation` is the intentionally explicit,
  security-sensitive inverse of `CEDARLING_JWT_SIG_VALIDATION`;
- filesystem inputs such as `CEDARLING_POLICY_STORE_LOCAL_FN` and
  `CEDARLING_LOCAL_JWKS` are not part of the Web-native public API;
- native-only settings such as asynchronous stdout buffers,
  `CEDARLING_HTTP_REQUEST_TIMEOUT`, and
  `CEDARLING_LOCK_ACCESS_TOKEN_JWT` do not apply to this WASM binding; and
- other raw settings, including policy-store entity-size limits and advanced
  Lock transport/dynamic-configuration controls, are not currently exposed.

If a WASM-relevant raw property needs to become public, treat that as a public
API change: add a typed option, validation and default behavior in
`prepare.ts`, mapping tests, public type contracts, and package README
documentation. Do not silently copy every new Rust bootstrap field into the
JavaScript API.

## WASM compatibility and fail-fast checks

The generated WASM package is an upstream interface, even though it lives in
the same repository. The SDK deliberately concentrates that dependency in the
engine and runtime-entry layers.

The package-level contract requires:

- the default asynchronous initializer and `initSync`;
- `init` and `init_from_archive_bytes`;
- the adjacent `cedarling_wasm_bg.wasm` asset;
- an initializer result exposing WebAssembly memory.

The client adapter depends on the generated authorization, issuer, context,
log, shutdown, and disposal methods. Returned result and context wrappers must
also retain their JSON/value accessors and `free()` methods.

An upstream rename, signature change, missing export, or missing binary should
fail before publication through several independent checks:

1. TypeScript compilation catches generated declaration drift.
2. The WASM producer contract checks required exports and the binary asset.
3. Engine-boundary unit tests verify SDK mapping and failure behavior.
4. Contract tests execute the built SDK against the real sibling WASM.
5. Runtime and packed-consumer tests verify conditional exports and loading.
6. Release staging verifies that the JavaScript package resolves the exact
   WASM version and build intended for publication.

When the generated API changes, update the adapter in `src/engine/` first.
Avoid letting generated types or objects leak into public exports: doing so
turns an internal producer change into a consumer breaking change.

## Tests and local gate

The shared test orchestrator loads the same suites in each runtime. Runners
should only prepare their host; behavioral assertions do not belong in
runner-specific copies.

Use focused commands while developing, then run the cumulative gate:

```sh
npm run test:types
npm run test:unit
npm run test:contract
npm run check
```

The cumulative gate expects Bun, Deno, and the Playwright browser binaries to
be installed. Use `npx playwright install` for the browser binaries; the
current tool versions used by CI are defined in
[`test-cedarling.yml`](../../../../.github/workflows/test-cedarling.yml).

For changes to the unsigned or multi-issuer authorization APIs, use the exact
suite filters accepted by the Node runner:

```sh
npm run test:unit -- authorize-unsigned
npm run test:contract -- authorize-unsigned
npm run test:unit -- authorize-multi-issuer
npm run test:contract -- authorize-multi-issuer
```

The focused suites divide responsibility as follows:

| Suite | Coverage |
| --- | --- |
| Unsigned unit | Rejects malformed request structures and unsafe Cedar values before invoking the engine |
| Unsigned real-WASM contract | Allow/deny results, structured actions, omitted-principal partial evaluation, detached principal/resource attributes, Cedar extension values, policy-store default entities, invalid entity types, and closed clients |
| Multi-issuer unit | Empty and invalid token inputs, detached token ordering, generated-wrapper disposal, and use of only the generated multi-issuer operation |
| Multi-issuer real-WASM contract | Valid, expired, not-yet-valid, malformed, unknown-issuer, partially invalid, and duplicate token sets; resource/default-entity precedence; and closed clients |

The multi-issuer contract fixture creates a correctly signed HS256 JWT, but its
client disables signature and status validation. This keeps the suite
deterministic and offline while exercising the SDK request mapping and real
WASM multi-issuer operation. It is not an end-to-end JWKS signature-validation
test; do not describe it as one. Signature/status validation behavior requires
separate integration coverage with controlled issuer endpoints.

`npm run check` covers the build, type contracts, unit and real-WASM contract
tests, supported runtime adapters, browser engines, packaged ESM/CommonJS
consumers, bundling, staging, and tarball validation. A change is not ready
because one runtime passed; the shared API and loading paths must remain
consistent across the matrix.

## Supported runtimes and known constraints

The support contract is encoded in `package.json` exports and CI:

| Runtime | Maintainer notes |
| --- | --- |
| Node.js | Minimum version is declared in `engines`; production support follows maintained Node release lines. |
| Browsers | Tested in Playwright Chromium, Firefox, and WebKit. WebKit coverage is not a claim that every Safari release is supported. The host CSP must permit WebAssembly compilation. |
| Bun and Deno | Use the Node-family byte-loading adapter. Deno tests currently require the permissions and compatibility flags encoded by the runner. |
| Electron | Main-process support uses the Node-family adapter. Renderer code must use the browser export graph. Test use of `--no-sandbox` is not deployment guidance. |
| Cloudflare workerd | Uses a statically imported WebAssembly module. Deployment remains subject to Worker compressed-size limits. |
| Vercel Edge | Uses an imported WebAssembly module. Local simulation cannot prove that a deployment fits the platform bundle limit. |

The WASM binary is large enough that edge deployment size must be checked
against the target plan during release validation. Do not infer deployability
from a local runtime test alone.

- [WebAssembly and Content Security Policy](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy#wasm-unsafe-eval)
- [Electron process model](https://www.electronjs.org/docs/latest/tutorial/process-model)
- [Electron sandboxing](https://www.electronjs.org/docs/latest/tutorial/sandbox)
- [Cloudflare Worker size limits](https://developers.cloudflare.com/workers/platform/limits/#worker-size)

## CI and release

Pull requests that change `jans-cedarling/**` run the `cedarling_js_tests` job
in [`test-cedarling.yml`](../../../../.github/workflows/test-cedarling.yml).
The job builds the scoped web-target WASM package from the checkout and runs
`npm run check` under Node.js 22 with the pinned Bun and Deno versions. The gate
also exercises Electron, workerd, Vercel Edge, Chromium, Firefox, WebKit, and
the packed ESM/CommonJS consumer tests. It never installs a previously
published WASM package.

[`build-packages.yml`](../../../../.github/workflows/build-packages.yml) owns npm
publication. `build_cedarling_wasm` uploads its generated web `pkg/` directory
as a short-lived workflow artifact. `build_cedarling_js` depends on that job,
downloads the artifact, stages the SDK tarball, and verifies that the SDK, its
WASM dependency, and the release all use the same exact version. The job waits
until that WASM version is visible on npm before publishing the wrapper.

Publication is triggered automatically after the repository build succeeds for
the `nightly` tag or a `vX.Y.Z` release tag. A maintainer can also dispatch
`build-packages.yml` with `run_cedarling_js`; that input automatically runs the
required WASM job first. Pull-request workflows never publish.

The package version and npm tag follow the release source:

| Release source | Package version | npm tag |
| --- | --- | --- |
| `nightly` | The generated `0.0.N` WASM version | `nightly` |
| `vX.Y.Z` | `X.Y.Z` | `latest` |
| `vX.Y.Z-prerelease` | `X.Y.Z-prerelease` | `next` |

The development manifest uses the repository nightly-version sentinel. The
release bump replaces it in the detached release-tag tree. For nightly builds,
the SDK reads the version from the downloaded WASM manifest; it does not keep a
separate nightly counter.

Publication is rerun-safe: an exact SDK version already present on npm is
skipped, while version mismatches or registry failures stop the job. Successful
publishes use npm trusted publishing with provenance. The SDK tarball is also
attached to the GitHub release, and its digest feeds the repository SLSA
provenance workflow. The npm package's trusted-publisher settings must authorize
`JanssenProject/jans` and `build-packages.yml`; the job receives
`id-token: write` and does not use a long-lived npm token.

Keep the WASM build, SDK tests, and publication order coupled. Testing against
an independently installed or previously published WASM package would miss
same-commit compatibility failures.

## Cargo workspace exception

The root `jans-cedarling/Cargo.toml` includes `bindings/*`, so
`bindings/cedarling_js` must remain in the workspace `exclude` list. It is an
npm package, not a Rust crate. Without the exclusion, workspace Cargo commands
attempt to treat it as a member and fail before reaching the real Rust
packages.

## Maintainer change checklist

- Public API change: update public types, type contracts, unit tests, and the
  package README.
- Generated WASM change: update the generated adapter and producer/real-WASM
  contracts.
- Runtime-loading change: update the relevant entry point and run the complete
  runtime and packed-consumer matrix.
- Export or packaging change: verify conditional exports, ESM/CommonJS,
  bundling, staging, and tarball contents.
- Release change: preserve the exact WASM-to-wrapper package and version
  relationship.
