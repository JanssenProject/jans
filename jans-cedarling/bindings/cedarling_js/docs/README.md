# Cedarling JavaScript maintainer guide

This document explains how `cedarling_js` is built and maintained. The
[package README](../README.md) is the authoritative consumer documentation.

## Repository location and build order

After cloning the Jans repository, the package is located at:

```text
jans-cedarling/bindings/cedarling_js
```

`cedarling_js` wraps the JavaScript glue generated by `cedarling_wasm`.
Building from source requires:

- Node.js 20.19 or later, including npm;
- the stable Rust toolchain with the `wasm32-unknown-unknown` target; and
- `wasm-pack` 0.14.0, matching the pull-request workflow.

Install the Rust target and pinned `wasm-pack` version when they are not
already available:

```sh
rustup toolchain install stable
rustup target add wasm32-unknown-unknown --toolchain stable
cargo install wasm-pack --version 0.14.0 --locked
```

Always build the sibling WASM package first, from its own directory:

```sh
cd jans-cedarling/bindings/cedarling_wasm
wasm-pack build --release --locked --target web --scope janssenproject

cd ../cedarling_js
npm ci
npm run check
```

Running `wasm-pack` inside `cedarling_wasm` is significant: its local Cargo
configuration controls the release profile used for the published binary.
The JavaScript package consumes `../cedarling_wasm/pkg` through the local
dependency declared in `package.json`. The cumulative `npm run check` gate
also requires Bun, Deno, and the Playwright browser binaries described in
[Tests and local gate](#tests-and-local-gate).

## Project structure

```text
cedarling_js/
├── src/                 SDK source
│   ├── entries/         Runtime-specific initialization selected by package exports
│   ├── configuration/   Public configuration validation and normalization
│   ├── client/          Public client behavior and lifecycle
│   ├── engine/          Boundary and adapters for the generated WASM API
│   ├── authorization/   Authorization request and response mapping
│   ├── context/         Context data operations and types
│   ├── issuers/         Trusted-issuer operations
│   ├── logs/            Decision-log operations and mapping
│   ├── values/          Shared value conversion
│   ├── helpers/         Fixed constants and host-neutral input mechanics
│   └── errors/          Stable errors and sensitive-detail redaction
├── tests/
│   ├── unit/            SDK behavior with controlled engine doubles
│   ├── contract/        Built SDK against the real sibling WASM
│   ├── e2e/             Packed consumers, module formats, bundlers, and browsers
│   ├── runners/         Host-specific launchers for shared suites
│   ├── fixtures/        Shared policy and runtime test inputs
│   └── tsconfig.json    Compile contract for SDK tests and public type usage
└── scripts/             Build, packaging, staging, and test orchestration
```

Runtime selection is internal. Consumers use the same `createCedarling` API in
every supported runtime and should follow the [package README](../README.md).

`src/helpers/constants.ts` is the single maintainer location for SDK fixed
values: typed defaults, numeric limits, accepted field sets, allowlists,
validation patterns, normalized error messages, and operation error policies.
Public literal types are derived from its canonical tuples. Keep dynamic state
and feature-specific behavior in their owning modules; do not introduce a
second fixed-value list beside a consumer.

`src/helpers/records.ts` owns descriptor-safe structural inspection, while
`src/helpers/validation.ts` builds reusable input rules on that interface.
Feature modules still choose accepted prototypes, validation paths, string
normalization, and error categories so consolidation does not erase domain
semantics.

## Initialization paths

The single `createCedarling(options)` factory accepts two mutually exclusive
configuration shapes:

- `WebNativeCedarlingOptions` is the curated JavaScript API. The preparation
  layer validates its stable SDK field names, applies SDK defaults, and maps
  them to Cedarling bootstrap properties.
- `RawBootstrapCedarlingOptions` contains `bootstrapProperties` plus the
  optional SDK-only `debug` policy. The preparation layer validates and
  snapshots the JSON object, then passes its keys and values to Cedarling core
  without mapping or inserting bootstrap defaults. `debug` never crosses the
  engine boundary.

Keeping both paths behind one factory preserves the discoverable Web-native
API while allowing immediate access to new core properties and parity with
other bindings. Never add SDK aliases to the raw path. The
[Cedarling bootstrap property reference](https://docs.jans.io/nightly/cedarling/reference/cedarling-properties/)
is its source of truth.

The configuration boundary is concentrated in
`src/configuration/prepare.ts`. Both paths must reject accessors without
executing them, detach caller-owned values before asynchronous work, and
reject mixed typed/raw inputs. Preparation also derives immutable client
capabilities, such as memory-log availability, the context TTL ceiling, and
whether raw causes may be exposed, once from the final configuration snapshot.
The engine receives only
`PreparedEngineOptions`; the client facade receives the separate
`PreparedClientCapabilities`. This keeps client behavior out of runtime
adapters and does not mutate or reinterpret the raw bootstrap map sent to
Cedarling core.

## Typed configuration mapping

The tables below document the curated `WebNativeCedarlingOptions` path. The
mapping implementation in `src/configuration/prepare.ts` remains the
maintainer source of truth. Defaults come from `src/helpers/constants.ts`.

The `RawBootstrapCedarlingOptions` path behaves differently: the SDK validates
and detaches the JSON-compatible `bootstrapProperties` object, then passes its
keys and values to Cedarling without aliases, inserted defaults, or value
translation. Consult the
[Cedarling bootstrap property reference](https://docs.jans.io/nightly/cedarling/reference/cedarling-properties/)
for that path. A core property does not become portable merely because it is
passed through to a WebAssembly runtime.

### Application, policy, and logging

| JavaScript option | Cedarling bootstrap behavior | Default or transformation |
| --- | --- | --- |
| `applicationName` | `CEDARLING_APPLICATION_NAME` | Required non-empty string |
| `policyStore: { type: "inline", document }` | `CEDARLING_POLICY_STORE_LOCAL` | Detached document serialized as JSON |
| `policyStore: { type: "url", url }` | `CEDARLING_POLICY_STORE_URI` | Normalized credential-free HTTPS or loopback HTTP URL |
| `policyStore.refresh.intervalSeconds` | `CEDARLING_POLICY_STORE_REFRESH_INTERVAL` | `0`; non-zero values must be at least 5 seconds |
| `policyStore: { type: "archive", bytes }` | Calls generated `init_from_archive_bytes` | No policy-source bootstrap property is inserted |
| `policyStore: { type: "loader", load }` | Invokes the loader once, then calls `init_from_archive_bytes` | No policy-source bootstrap property is inserted |
| `logging` omitted or `{ type: "off" }` | `CEDARLING_LOG_TYPE=off`, `CEDARLING_LOG_LEVEL=WARN` | Logging disabled |
| `logging.type: "memory"` | `CEDARLING_LOG_TYPE=memory` | Enables `client.logs` |
| `logging.type: "console"` | `CEDARLING_LOG_TYPE=std_out` | Writes through the generated console logger |
| `logging.level` | `CEDARLING_LOG_LEVEL` | `"warn"`, converted to the uppercase core value |
| `logging.ttlSeconds` | `CEDARLING_LOG_TTL` | `60`; memory logging only |
| `logging.maxItems` | `CEDARLING_LOG_MAX_ITEMS` | `10_000`; zero removes the count limit |
| `logging.maxItemSizeBytes` | `CEDARLING_LOG_MAX_ITEM_SIZE` | `500_000`; zero removes the size limit |

`logging.type` is the typed JavaScript selector for the existing
`CEDARLING_LOG_TYPE` property, not a second logging system. Lock delivery is
configured separately through `lock`. See the
[Cedarling audit-log reference](https://docs.jans.io/nightly/cedarling/reference/cedarling-logs/#cedarling-audit-logs)
for the core logging modes.

### Authorization and JWT validation

| JavaScript option | Cedarling bootstrap behavior | Default or transformation |
| --- | --- | --- |
| `authorization.dangerouslyDisableSchemaValidation` | Inverts to `CEDARLING_STRICT_SCHEMA_VALIDATION` | `false` maps to `enabled` |
| `authorization.decisionLogTokenIdClaim` | `CEDARLING_DECISION_LOG_DEFAULT_JWT_ID` | `"jti"` |
| `jwt.dangerouslyDisableSignatureValidation` | Inverts to `CEDARLING_JWT_SIG_VALIDATION` | `false` maps to `enabled` |
| `jwt.dangerouslyDisableStatusValidation` | Inverts to `CEDARLING_JWT_STATUS_VALIDATION` | `false` maps to `enabled` |
| `jwt.allowedAlgorithms` | `CEDARLING_JWT_SIGNATURE_ALGORITHMS_SUPPORTED` | All exported `JwtAlgorithm` values when omitted |
| `jwt.jwksRefreshIntervalSeconds` | `CEDARLING_JWKS_REFRESH_INTERVAL` | Property omitted when unspecified; supplied values must be at least 5 seconds |
| `jwt.jwksRefreshMinIntervalSeconds` | `CEDARLING_JWKS_REFRESH_MIN_INTERVAL` | `30` seconds |
| `jwt.statusListRefreshMaxSeconds` | `CEDARLING_JWT_STATUS_LIST_REFRESH_INTERVAL_MAX` | `300` seconds |

The dangerous validation flags expose existing Cedarling controls with names
that make the security consequence explicit. They do not perform or bypass an
additional SDK validation pass. Omitting `jwt.allowedAlgorithms` enables all
twelve algorithms represented by the SDK type, including symmetric HS
algorithms; production consumers should configure the smallest allowlist
required by their trusted issuers.

`debug.dangerouslyExposeRawErrors` is SDK-only. It controls whether an
original, potentially secret-bearing failure can be exposed as a
non-enumerable `error.cause`; it is never forwarded as a bootstrap property.

## Consumer service map

`createCedarling(options)` returns one `CedarlingClient`. Every service shares
that client's engine instance, configuration, and lifecycle.

| Consumer surface | Features exposed | SDK responsibility before and after WASM |
| --- | --- | --- |
| `client.authorizeUnsigned()` | Authorize application-supplied Cedar entities, action, resource, and context | Validate and detach the request, invoke unsigned authorization, and normalize the decision or error |
| `client.authorizeMultiIssuer()` | Validate mapped JWTs from configured issuers and authorize the resulting entities | Validate token mappings and request shape, invoke multi-issuer authorization, and normalize the result |
| `client.context` | `set`, `get`, `getEntry`, `delete`, `clear`, `entries`, and `stats` | Validate keys, values, and TTLs; detach inputs and outputs; delegate storage and authorization-time context injection to Cedarling |
| `client.issuers` | `isLoaded` by configured issuer ID or exact `iss` value | Require exactly one issuer reference, then normalize the readiness observation |
| `client.logs` | `ids`, filtered `find`, and destructive `drain` | Validate supported query combinations, enforce memory-logging availability, and return detached, normalized log entries |
| `client.shutDown()` | Shut down the client and release WASM resources | Reject new work once shutdown starts, wait for accepted operations, perform shutdown once, and share the result across repeated calls |

The SDK makes these decisions independently of the Cedarling engine:

- package export conditions select the runtime adapter; there is no runtime
  detection in the public API;
- public configuration and operation inputs are validated, copied, and
  detached before crossing the WASM boundary;
- authorization requests, actions, entities, and token inputs reject unknown
  fixed-shape fields, while entity attributes and request context remain open
  Cedar data containers;
- expected failures use the stable `Result` and SDK error model, with
  validation paths and redacted details;
- original adapter failures stay in private weak metadata unless the consumer
  explicitly enables `debug.dangerouslyExposeRawErrors`; the exposed `cause`
  is non-enumerable but remains secret-bearing and unsafe to log;
- authorization exposes only the two named trust-model operations, and each
  returns the canonical
  `Result<AuthorizationDecision, CedarlingAuthorizationError>` shape;
- generated decisions, context values, issuer observations, and logs are
  converted into stable JavaScript-owned values;
- operations share one lifecycle guard, and `shutDown()` coordinates
  concurrent work and disposal.

The SDK does not independently decide whether access is allowed, whether a
token or issuer is trusted, or how a Cedar policy evaluates. Those decisions
remain in Cedarling WASM; the SDK validates the JavaScript contract, delegates
the operation, and stabilizes the result.

## WASM compatibility and fail-fast checks

The generated WASM package is an upstream interface, even though it lives in
the same repository. The SDK deliberately concentrates that dependency in the
engine and runtime-entry layers.

The package-level contract requires:

- the default asynchronous initializer and `initSync`;
- `init` and `init_from_archive_bytes`;
- the adjacent `cedarling_wasm_bg.wasm` asset;
- an initializer result exposing WebAssembly memory.

Generated authorization, shutdown, and disposal methods are required when
the client wrapper is adapted. Issuer, context, and log methods remain lazily
validated when their corresponding SDK operation is invoked. All lazy method
lookups share one receiver-safe invocation boundary and report the public
operation as `GENERATED_PROTOCOL_ERROR` when the generated protocol is
incompatible. Returned result and context wrappers must retain their
JSON/value accessors and `free()` methods, and the SDK must dispose them on
both success and failure paths.

An upstream rename, signature change, missing export, or missing binary should
fail before publication through several independent checks:

1. TypeScript compilation catches generated declaration drift.
2. The WASM producer contract checks required exports and the binary asset.
3. Engine-boundary unit tests verify SDK mapping and failure behavior.
4. Contract tests execute the built SDK against the real sibling WASM.
5. Runtime and packed-consumer tests verify conditional exports and loading.
6. Release staging verifies that the JavaScript package resolves the exact
   WASM version and build intended for publication.

When the generated API changes, update the adapter in `src/engine/` first.
Avoid letting generated types or objects leak into public exports: doing so
turns an internal producer change into a consumer breaking change.

## Tests and local gate

The shared test orchestrator loads the same suites in each runtime. Runners
should only prepare their host; behavioral assertions do not belong in
runner-specific copies.

Use the underlying test commands with a suite filter during development:

```sh
npm run test:unit -- authorize-unsigned
npm run test:contract -- authorize-unsigned
npm run test:unit -- authorize-multi-issuer
npm run test:contract -- authorize-multi-issuer
npm run test:e2e
npm run check
```

The focused authorization suites divide responsibility as follows:

| Suite | Coverage |
| --- | --- |
| Unsigned unit | Malformed and unknown request fields, accessor rejection, unsafe Cedar values, and generated-wrapper disposal |
| Unsigned real-WASM contract | Allow/deny decisions, structured actions, omitted principals, detached entity attributes, Cedar extension values, policy-store default entities, invalid entity types, and closed clients |
| Multi-issuer unit | Empty and invalid token inputs, detached token ordering, generated-wrapper disposal, and exclusive use of the generated multi-issuer operation |
| Multi-issuer real-WASM contract | Valid, expired, not-yet-valid, malformed, unknown-issuer, partially invalid, and duplicate token sets; resource/default-entity precedence; and closed clients |

The focused multi-issuer contract fixture uses structurally signed synthetic
tokens but disables signature and status validation so the suite stays offline
and isolates request/result behavior. Cryptographic verification is covered
separately by `tests/e2e/signature-validation.test.ts`, which serves a
controlled local OpenID configuration and JWKS, keeps signature validation
enabled, accepts a valid RS256 token, and rejects a tampered signature, expired
or untrusted claims, and an algorithm outside the configured allowlist.

Every CI-sized stage also has a self-contained `test:*` command. Each stage
prepares the build it needs, so future CI jobs can run independently without
depending on artifacts left by an earlier check:

| Command | Coverage |
| --- | --- |
| `npm run test:types` | ESM/CommonJS build, SDK typecheck, and no-emit compilation of the maintained test tree |
| `npm run test:unit` | Node unit suites, producer contract, and publishable-manifest checks |
| `npm run test:contract` | Public contract against the real sibling WASM package in Node |
| `npm run test:node` | Unit and real-WASM contract suites under Node |
| `npm run test:bun` | Unit and portable real-WASM contracts under Bun |
| `npm run test:deno` | Unit and portable real-WASM contracts under Deno |
| `npm run test:electron` | Unit and portable real-WASM contracts in Electron main |
| `npm run test:workerd` | Unit and portable real-WASM contracts in workerd |
| `npm run test:browser` | Browser suites in Playwright Chromium, Firefox, and WebKit |
| `npm run test:vercel-edge` | Portable contracts in the Vercel Edge simulator |
| `npm run test:e2e` | Signed-token behavior, packed ESM/CommonJS consumers, browser bundling, and release staging |
| `npm run test:all-runtimes` | All Node, runtime, browser, and E2E stages above |
| `npm run pack:dry-run` | Coordinated SDK/WASM staging and tarball dry run |
| `npm run check` | Types, all runtime tests, E2E tests, and package staging as the cumulative release gate |

The pull-request workflow invokes the `test:*` commands as named stages and
runs `pack:dry-run` last, so failures identify the affected runtime. A change is
not ready merely because one stage passed: run the cumulative `npm run check`
before handoff.

## Supported runtimes and known constraints

The support contract is encoded in `package.json` exports and CI:

| Runtime | Maintainer notes |
| --- | --- |
| Node.js | Minimum version is declared in `engines`; production support follows maintained Node release lines. |
| Browsers | Tested in Playwright Chromium, Firefox, and WebKit. WebKit coverage is not a claim that every Safari release is supported. The host CSP must permit WebAssembly compilation. |
| Bun and Deno | Use the Node-family byte-loading adapter. Deno tests currently require the permissions and compatibility flags encoded by the runner. |
| Electron | Main-process support uses the Node-family adapter. Renderer code must use the browser export graph. Test use of `--no-sandbox` is not deployment guidance. |
| Cloudflare workerd | Uses a statically imported WebAssembly module. Deployment remains subject to Worker compressed-size limits. |
| Vercel Edge | Uses an imported WebAssembly module. Local simulation cannot prove that a deployment fits the platform bundle limit. |

The WASM binary is large enough that edge deployment size must be checked
against the target plan during release validation. Do not infer deployability
from a local runtime test alone.

## CI and release

Pull requests that change `jans-cedarling/**` run the `cedarling_js_tests` job
in [`test-cedarling.yml`](../../../../.github/workflows/test-cedarling.yml).
The job builds the scoped web-target WASM package from the checkout and runs
the individual `test:*` stages under Node.js 22 with the pinned Bun and Deno
versions, followed by the package dry run. The gate also exercises Electron,
workerd, Vercel Edge, Chromium, Firefox, WebKit, and the packed ESM/CommonJS
consumer tests. It never installs a previously published WASM package.

[`build-packages.yml`](../../../../.github/workflows/build-packages.yml) owns npm
publication. `build_cedarling_wasm` uploads its generated web `pkg/` directory
as a short-lived workflow artifact. `build_cedarling_js` depends on that job,
downloads the artifact, stages the SDK tarball, and verifies that the SDK, its
WASM dependency, and the release all use the same exact version. The job waits
until that WASM version is visible on npm before publishing the wrapper.
Because the dependency is a generated local package, the job synchronizes its
CI-only lockfile before the strict `npm ci` install. Release staging receives
the coordinated version explicitly and does not mutate the source manifest.

Publication is triggered automatically after the repository build succeeds for
the `nightly` tag or a `vX.Y.Z` release tag. A maintainer can also dispatch
`build-packages.yml` with `run_cedarling_js`; that input automatically runs the
required WASM job first. Pull-request workflows never publish.

The package version and npm tag follow the release source:

| Release source | Package version | npm tag |
| --- | --- | --- |
| `nightly` | The downloaded generated WASM package version | `nightly` |
| `vX.Y.Z` | `X.Y.Z` | `latest` |
| `vX.Y.Z-prerelease` | `X.Y.Z-prerelease` | `next` |

The development manifest uses the `0.0.0-nightly` sentinel. For nightly
publication, the workflow reads the downloaded WASM manifest and supplies that
exact version to release staging. For a release tag, both the source SDK
manifest and the downloaded WASM package must already match the version encoded
by the tag. The SDK does not maintain an independent nightly counter.

Publication is rerun-safe: an exact SDK version already present on npm is
skipped, while version mismatches or registry failures stop the job. Successful
publishes use npm trusted publishing with provenance. The SDK tarball is also
attached to the GitHub release, and its digest feeds the repository SLSA
provenance workflow. The npm package's trusted-publisher settings must authorize
`JanssenProject/jans` and `build-packages.yml`; the job receives
`id-token: write` and does not use a long-lived npm token.

Trusted publishing can be configured only after the package exists on npm. A
maintainer must therefore publish the inspected SDK tarball once, then authorize
`JanssenProject/jans` and `build-packages.yml` in the package settings before
the automated publication job is enabled. The job checks that the package
exists and fails with an actionable error instead of attempting token
authentication; npm remains the source of truth for the trusted-publisher
configuration.

Keep the WASM build, SDK tests, and publication order coupled. Testing against
an independently installed or previously published WASM package would miss
same-commit compatibility failures.

## Cargo workspace exception

The root `jans-cedarling/Cargo.toml` includes `bindings/*`, so
`bindings/cedarling_js` must remain in the workspace `exclude` list. It is an
npm package, not a Rust crate. Without the exclusion, workspace Cargo commands
attempt to treat it as a member and fail before reaching the real Rust
packages.

## Maintainer change checklist

- Public API change: update public types, type contracts, unit tests, and the
  package README.
- Generated WASM change: update the generated adapter and producer/real-WASM
  contracts.
- Runtime-loading change: update the relevant entry point and run the complete
  runtime and packed-consumer matrix.
- Export or packaging change: verify conditional exports, ESM/CommonJS,
  bundling, staging, and tarball contents.
- Release change: preserve the exact WASM-to-wrapper package and version
  relationship.
